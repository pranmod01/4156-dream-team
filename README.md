# Resource Allocator API

This project implements a simple resource allocation service. Organizations can register with the service, list the available resources (CPUs and GPUs), set usage limits, and take specific resources offline. Other clients can then request specific resources for their jobs, and the job will be added to the queue.

## To Set Up and Run Locally
1. Install PostgreSQL and start it on port 5432.
2. Run the database setup script using `./scripts/setup-db.sh` (for Windows, `PGUSER=postgres ./scripts/setup-db.sh`).
    - Creates the user called `resource_allocator` and with password `dev_password`
    - Creates a database called `resource_allocator_db`
    - Alternatively, set your own username, password, and database name. Set these in a `.env` file
3. Start the app with `./mvnw spring-boot:run`. Flyway will create the tables on startup.

If your setup differs (port, user, database, or password), create an `.env` file based on `.env.example`.

NOTE: dev_password is for local use only. Do not expose your Postgres to external connections.

## Using the API

### Authentication
`POST /clients` is the only endpoint that does not need authentication. It returns an `apiKey`, which must be sent in the `X-API-Key` header on every `/jobs` and `/resources` request. The key is shown only once: the server stores only its SHA-256 hash, so a lost key cannot be recovered. A missing or unknown key returns `401` before the request body is validated.

Each organization sees and uses only its own resources and jobs. Asking for another organization's job or resource by ID behaves as if it does not exist.

### Call Order
1. `POST /clients` to register an organization and get its API key.
2. `POST /resources` to register at least one CPU or GPU. Without online resources, jobs stay `QUEUED` with `blockedReason: NO_MATCHING_RESOURCE`.
3. `POST /jobs` to submit work.
4. `GET /jobs/{jobId}` or `GET /jobs/queue` to track progress.
5. `DELETE /jobs/{jobId}` to remove a job once it is no longer running. `PATCH /resources/{resourceId}` to take a resource offline once no job is using it.

### Side Effects and Scheduling
- **The dispatcher** moves jobs through `QUEUED` → `RUNNING` → `DONE`. It ends running jobs whose lease (`maxDurationHours`) has expired, then starts queued jobs that have enough free online resources and fit within the usage limit.
- It runs at the start of every `/jobs` request (`POST /jobs`, `GET /jobs/{jobId}`, `DELETE /jobs/{jobId}`, `GET /jobs/queue`), so their responses are always current.
- It also runs in the background every 30 seconds for each organization with unfinished jobs (set with `dispatcher.interval-ms`).
- `POST /resources` and `PATCH /resources/{resourceId}` do **not** start queued jobs. A newly added or re-enabled resource is picked up on the next `/jobs` request or background run. When taking a resource offline, `PATCH` first marks jobs whose lease has expired as `DONE`, so a resource whose job just finished can be taken offline.
- **Usage limits:** `maxCpus`/`maxGpus` cap the units an organization's *running* jobs hold at once. A job asking for more than the limit is rejected with `400`. A job within the limit that would push the running total over it waits in the queue (`blockedReason: EXCEEDS_USAGE_LIMIT`).
- **Queue order:** queued jobs are tried oldest first, but scheduling is not strict first-come-first-served. If the oldest job can't start, a newer job that fits may start ahead of it.
- **Deleting a job** also deletes its resource assignments.

### Example: Correct Usage
With the app running on `localhost:8080`:
```
# 1. Register an organization (no key needed). Save the apiKey from the response.
curl -X POST localhost:8080/clients -H 'Content-Type: application/json' \
  -d '{"orgName": "lab-a", "maxCpus": 4, "maxGpus": 1}'
# -> 201 {"id": 1, "orgName": "lab-a", "maxCpus": 4, "maxGpus": 1, "createdAt": "...", "apiKey": "<KEY>"}

# 2. Register a CPU.
curl -X POST localhost:8080/resources -H 'X-API-Key: <KEY>' -H 'Content-Type: application/json' \
  -d '{"resourceType": "CPU", "memoryGb": 64, "cores": 8, "online": true}'
# -> 201 {"id": 1, "resourceType": "CPU", "memoryGb": 64, "cores": 8, "online": true}

# 3. Submit a job that fits the CPU. It starts immediately.
curl -X POST localhost:8080/jobs -H 'X-API-Key: <KEY>' -H 'Content-Type: application/json' \
  -d '{"resourceType": "CPU", "unitsRequested": 1, "minMemoryGb": 32, "minCores": 4, "maxDurationHours": 2}'
# -> 201 {"jobId": 1, "status": "RUNNING", ..., "resourceIds": [1]}

# 4. Submit the same job again. The only CPU is busy, so it waits.
# -> 201 {"jobId": 2, "status": "QUEUED", ..., "resourceIds": []}

# 5. Check the queue.
curl localhost:8080/jobs/queue -H 'X-API-Key: <KEY>'
# -> 200: job 1 is RUNNING; job 2 has queuePosition 1, blocked: true, blockedReason: RESOURCES_IN_USE
#    summary: {"queued": 1, "running": 1, "done": 0}

# 6. Delete the queued job.
curl -X DELETE localhost:8080/jobs/2 -H 'X-API-Key: <KEY>'
# -> 200 {"deletedJobId": 2}
```

### Example: Incorrect Usage
Continuing from the session above (job 1 is running on resource 1, and `maxCpus` is 4):

| Misuse | Response |
|---|---|
| `POST /resources` with no `X-API-Key` header | `401` "Missing X-API-Key header." |
| `POST /jobs` for a CPU job without `minCores` | `400` "minCores is required for CPU jobs." |
| `POST /jobs` with `"unitsRequested": 5` | `400` "unitsRequested exceeds the organization's CPU limit of 4." |
| `DELETE /jobs/1` while job 1 is running | `409` "Job 1 is running and cannot be deleted." |
| `PATCH /resources/1` with `{"online": false}` while job 1 uses it | `409` "Resource 1 is in use by a running job." |
| `PATCH /resources/999`, a resource that doesn't exist or belongs to another organization | `404` "Resource 999 was not found." |

## API Endpoints

### Common Responses
- `400 Bad Request` -- The request is malformed or fails validation.
- `401 Unauthorized` -- The `X-API-Key` header is missing or does not match any organization. Applies to every `/jobs` and `/resources` endpoint.

Every error response uses the standard problem-details JSON format (RFC 9457):
```
{
    "title": "Bad Request",
    "status": 400,
    "detail": "minCores is required for CPU jobs.",
    "instance": "/jobs"
}
```
When the request body fails validation, the response also includes an `errors` list naming each invalid field:
```
{
    "title": "Bad Request",
    "status": 400,
    "detail": "Request body failed validation.",
    "instance": "/clients",
    "errors": ["maxCpus: must be greater than or equal to 0"]
}
```

### POST /clients
- Creates a new client, allowing a new organization to register resources and set usage limits
- Request Body:
    ```
    {
        "orgName": "name",
        "maxCpus": 0,
        "maxGpus": 0
    }
    ```
    - orgName (string, required): Unique organization name, max 255 characters
    - maxCpus (integer, required): Maximum number of CPU units an organization can have running simultaneously. Must be nonnegative.
    - maxGpus (integer, required): Maximum number of GPU units an organization can have running simultaneously. Must be nonnegative.

- Responses:
    - `201 Created` -- Organization created successfully. Returns organization information with API key.
    ```
    {
        "id": 1,
        "orgName": "name",
        "maxCpus": 1,
        "maxGpus": 1,
        "createdAt": "2026-10-22T01:19:54.460571Z",
        "apiKey": "fy992aNbxo1342oAd7O9FBDFd73QBtDJ1hWYFzOLsUs"
    }
    ```
    - `409 Conflict` -- Returns conflict if the name is not unique


### POST /jobs
- Creates a job, specifying the minimum CPU or GPU resources required. If CPUs are requested, `minCores` is required. Otherwise, `minCores` must be null. The endpoint also checks if this job is allowed to be run under the current usage limits. 
- Authentication: required
- Request Body: 
    ```
    {
        "resourceType": "CPU",
        "unitsRequested": 1,
        "minMemoryGb": 64,
        "minCores": 4,
        "maxDurationHours": 3
    }
    ```
    - resourceType (required)
    - unitsRequested (integer, required): The number of CPU or GPU units required. Must be positive.
    - minMemoryGb (integer, required): The minimum amount of memory needed for the unit. Must be positive.
    - minCores (integer): The number of cores required for a CPU request. Must be positive. Must be null if requesting GPU.
    - maxDurationHours (integer, required): A lease on the maximum amount of time this job can hold the resource. Must be positive.

- Responses:
    - `201 Created` -- Job created successfully. Returns job information, along with its current status, when the job was started, and associated resource IDs.
        ```
        {
            "jobId": 1,
            "status": "QUEUED",
            "resourceType": "CPU",
            "unitsRequested": 1,
            "submittedAt": "2026-10-22T01:19:54.460571Z",
            "startedAt": null,
            "leaseEnd": null,
            "resourceIds": []
        }
        ```
    - `400 Bad Request` -- Also returned if `minCores` is missing for a CPU job or set for a GPU job. This is also returned if `unitsRequested` exceeds the organization's usage limit for that resource type.


### GET /jobs/{jobId}
- Returns a job's current status, including when it started, when its lease ends, and which resources it has been assigned.
- Before responding, the server dispatches any queued jobs that can now run, so the returned status is up to date.
- Authentication: required
- Path Parameters:
    - jobId (integer, required): The ID of the job, as returned when the job was created.

- Responses:
    - `200 OK` -- Returns the job's information.
        ```
        {
            "jobId": 1,
            "status": "RUNNING",
            "resourceType": "CPU",
            "unitsRequested": 1,
            "submittedAt": "2026-10-22T01:19:54.460571Z",
            "startedAt": "2026-10-22T01:19:54.512034Z",
            "leaseEnd": "2026-10-22T04:19:54.512034Z",
            "resourceIds": [3]
        }
        ```
    - `400 Bad Request` -- Also returned if the organization has no job with the given ID.


### DELETE /jobs/{jobId}
- Permanently deletes a job that is not currently running (i.e., `QUEUED` or `DONE`), along with any of its resource assignments.
- Running jobs cannot be deleted.
- Authentication: required
- Path Parameters:
    - jobId (integer, required): The ID of the job to delete.

- Responses:
    - `200 OK` -- Job deleted successfully. Returns the ID of the deleted job.
        ```
        {
            "deletedJobId": 1
        }
        ```
    - `404 Not Found` -- The organization has no job with the given ID.
    - `409 Conflict` -- The job is currently running and cannot be deleted.


### GET /jobs/queue
- Lists the organization's jobs in queue order (oldest submission first), with optional filters.
- Queued jobs include their position in the queue and, if they cannot run yet, why they are blocked. Also returns a count of jobs in each status.
- Authentication: required
- Query Parameters (all optional; values are case-insensitive):
    - status (string): Only return jobs in this state. One of `QUEUED`, `RUNNING`, `DONE`.
    - resourceType (string): Only return jobs requesting this resource type. One of `CPU`, `GPU`.
    - start (ISO-8601 timestamp): Only return running or done jobs whose run overlaps a window starting at this time. Queued jobs are always included.
    - end (ISO-8601 timestamp): Only return running or done jobs whose run overlaps a window ending at this time. Must not be before `start`.
    - limit (integer): Maximum number of jobs to return. Must be positive.
- Example Request: `GET /jobs/queue?status=queued&resourceType=CPU&limit=10`

- Responses:
    - `200 OK` -- Returns the matching jobs and a summary of job counts by status. `queuePosition` is null for jobs that are not queued, and `blockedReason` is set when `blocked` is true: `NO_MATCHING_RESOURCE` (not enough online resources meet the job's requirements), `RESOURCES_IN_USE` (enough match, but running jobs hold them), or `EXCEEDS_USAGE_LIMIT` (starting the job would exceed the organization's usage limit).
        ```
        {
            "jobs": [
                {
                    "jobId": 2,
                    "status": "QUEUED",
                    "requiredResources": {
                        "resourceType": "CPU",
                        "unitsRequested": 1,
                        "minMemoryGb": 64,
                        "minCores": 4,
                        "maxDurationHours": 3
                    },
                    "submittedAt": "2026-10-22T01:19:54.460571Z",
                    "startedAt": null,
                    "leaseEnd": null,
                    "queuePosition": 1,
                    "blocked": true,
                    "blockedReason": "NO_MATCHING_RESOURCE"
                }
            ],
            "summary": {
                "queued": 1,
                "running": 0,
                "done": 0
            }
        }
        ```
    - `400 Bad Request` -- Also returned if `status` or `resourceType` is not a recognized value, a timestamp is malformed, `end` is before `start`, or `limit` is not positive.


### POST /resources
- Registers a new CPU or GPU resource for the organization. If registering a CPU, `cores` is required. Otherwise, `cores` must be null.
- Resources that are online can be assigned to queued jobs.
- Authentication: required
- Request Body:
    ```
    {
        "resourceType": "CPU",
        "memoryGb": 64,
        "cores": 8,
        "online": true
    }
    ```
    - resourceType (string, required): Type of resource. One of `CPU`, `GPU`.
    - memoryGb (integer, required): Amount of memory on the resource. Must be positive.
    - cores (integer): Number of cores on a CPU resource. Must be positive. Must be null for a GPU.
    - online (boolean, required): Whether the resource is available to run jobs.

- Responses:
    - `201 Created` -- Resource created successfully. Returns the resource's information.
        ```
        {
            "id": 1,
            "resourceType": "CPU",
            "memoryGb": 64,
            "cores": 8,
            "online": true
        }
        ```
    - `400 Bad Request` -- Also returned if `cores` is missing for a CPU resource or set for a GPU resource.


### GET /resources
- Lists all of the organization's resources, ordered by ID, along with whether each is online.
- Authentication: required

- Responses:
    - `200 OK` -- Returns a list of the organization's resources.
        ```
        [
            {
                "id": 1,
                "resourceType": "CPU",
                "memoryGb": 64,
                "cores": 8,
                "online": true
            },
            {
                "id": 2,
                "resourceType": "GPU",
                "memoryGb": 80,
                "cores": null,
                "online": false
            }
        ]
        ```


### PATCH /resources/{resourceId}
- Takes one of the organization's resources online or offline. 
- If a resource is in use, taking it offline will fail. The endpoint will block any new dispatches, check the job queue for any finished jobs, and then attempt to take the resource offline. 
- Authentication: required
- Path Parameters:
    - resourceId (integer, required): The ID of the resource to update.
- Request Body:
    ```
    {
        "online": false
    }
    ```
    - online (boolean, required): The new online state of the resource.

- Responses:
    - `200 OK` -- Resource updated successfully. Returns the updated resource's information.
        ```
        {
            "id": 1,
            "resourceType": "CPU",
            "memoryGb": 64,
            "cores": 8,
            "online": false
        }
        ```
    - `404 Not Found` -- Returned if there is no resource with an ID associated with the organization.
    - `409 Conflict` -- Returned if attempting to take a resource offline while it is still running a job.
